# Current State

## Active architectural decisions
Sacrifice currently ships a real app runtime and a separate agent-facing repo workflow. The runtime is the FastAPI API plus Celery plus the Expo app; the repo workflow is described in `PROMPT.md`, `activity.md`, and `opencode.json`. There is no in-app generator runner or chat subsystem in the files read, so the generator direction currently lives at the repository boundary rather than in shipped product code (`backend/app/main.py`, `backend/app/core/celery_app.py`, `frontend/App.tsx`, `PROMPT.md`, `opencode.json`).

Goal verification is the most dynamic part of the system today. `app.goal_types.registry` auto-discovers subpackages under `backend/app/goal_types/`, `GET /api/goal-types` returns their metadata, and the smoke tests prove a newly created subpackage can be discovered without central registry edits as long as it exposes a module-level `goal_type` instance and supporting metadata/verifier files (`backend/app/goal_types/registry.py`, `backend/app/routes/goals.py`, `backend/tests/test_goal_type_smoke.py`, `backend/tests/test_goal_type_registry.py`).

Goal creation is still static even though goal verification is discovered dynamically. The client hard-codes a `GoalType` union and type-specific criteria editors for exactly four goal types, `GoalCreate` validates the same four strings, and the database stores those names in SQL enums for both `Goal.goal_type` and `GoalCriteria.criteria_type` (`frontend/screens/GoalCreateScreen.tsx`, `backend/app/schemas/goal.py`, `backend/app/models/goal.py`). A generated plugin package can be discovered by the registry today, but it cannot yet be selected and persisted end-to-end without widening those creation-time constraints.

The live proof contract is route-driven JSON, not a media/upload pipeline. `ProofSubmissionCreate` is a flat union-like schema of URL, API, repo, and token fields; the frontend request helper always sends JSON; and the YouTube proof screen is still a text input for a pasted URL (`backend/app/schemas/proof.py`, `frontend/services/api.ts`, `frontend/screens/ProofSubmissionScreen.tsx`). `submit_proof()` in `routes/goals.py` flattens that body with `model_dump()`, calls `goal_type.verify(proof_data, criteria_data)`, persists `proof_data` and later `verification_details` as JSONB, and only then best-effort invokes `dispatch_verification()` if the plugin exposes it (`backend/app/routes/goals.py`, `backend/app/models/proof.py`).

The abstract plugin API is slightly ahead of the route contract. `GoalTypeBase` defines optional `submit_proof()` and `dispatch_verification()` hooks, and concrete goal types such as `youtube_video` and `api_endpoint` implement both, but the current `submit_proof()` route does not call `submit_proof()` at all; it calls `verify()` directly on the flattened request body (`backend/app/goal_types/base.py`, `backend/app/goal_types/youtube_video/__init__.py`, `backend/app/goal_types/api_endpoint/__init__.py`, `backend/app/routes/goals.py`, `backend/tests/test_goal_dispatch.py`). For generator work, the route's real contract matters more than the abstract class alone.

Celery inclusion is also only partially conventional. `get_celery_include_modules()` derives worker modules as `app.workers.<goal_type>`, but the concrete built-in plugins dispatch to `app.workers.youtube` and `app.workers.api_check` instead of `app.workers.youtube_video` and `app.workers.api_endpoint` (`backend/app/goal_types/registry.py`, `backend/app/core/celery_app.py`, `backend/app/goal_types/youtube_video/__init__.py`, `backend/app/goal_types/api_endpoint/__init__.py`, `backend/app/workers`). A generator cannot rely on naming convention alone unless that mismatch is normalized.

A phone-camera-backed physical proof path is still absent. Navigation has no capture screen, Expo config has no camera/media plugin, the frontend transport has no `FormData` or upload helper, and the backend mounts no upload route or media schema (`frontend/hooks/useNavigation.tsx`, `frontend/app.json`, `frontend/services/api.ts`, `backend/app/main.py`, `backend/app/schemas/proof.py`). That missing infrastructure is the main blocker between today's registry-friendly plugin system and a future `pushup_counter`-style goal type.

## Current constraints
- `PROMPT.md` says the orchestrator already runs backend and frontend, so repo tasks should edit against the live auto-reloading services rather than starting new copies by default (`PROMPT.md`).
- Frontend/mobile work must stay aligned with Expo 54.0.0 docs because the repo explicitly pins that documentation version for agent work (`frontend/AGENTS.md`, `frontend/package.json`).
- Generated goal types can satisfy registry discovery if they are written as new subpackages under `backend/app/goal_types/`, but they still cannot be created through the current app without extending frontend forms, backend validators, and database enums (`backend/app/goal_types/registry.py`, `backend/tests/test_goal_type_smoke.py`, `frontend/screens/GoalCreateScreen.tsx`, `backend/app/schemas/goal.py`, `backend/app/models/goal.py`).
- Generated proof logic must currently accept a JSON request body shaped like `ProofSubmissionCreate`; there is no upload token, media asset ID, or multipart contract in the current backend/frontend pair (`backend/app/schemas/proof.py`, `frontend/services/api.ts`, `backend/app/routes/goals.py`).
- `ProofSubmission` persistence is generic enough for generator work because both `proof_data` and `verification_details` are JSONB, but the route still treats verification as a mostly synchronous registry call with optional async dispatch afterward (`backend/app/models/proof.py`, `backend/app/routes/goals.py`).
- The built-in worker naming is inconsistent with the registry's include-module convention, so generated async verification should expose an explicit `dispatch_verification()` unless worker naming is standardized first (`backend/app/goal_types/registry.py`, `backend/app/goal_types/youtube_video/__init__.py`, `backend/app/goal_types/api_endpoint/__init__.py`, `backend/app/workers`).
