# Current state

## Active architectural decisions
Sacrifice runs as one FastAPI service that wires together health, auth, dashboard, goal-type listing, goal CRUD/proof submission, notifications, payment, uploads, chat, and webhook routes in `backend/app/main.py`. The backend exposes one authenticated HTTP surface to both the Expo client and OAuth browser callbacks, rather than separate mobile and automation backends (`backend/app/main.py`).

Authentication is JWT-based but anchored to mutable server-side session state. Access tokens are signed with `jwt_secret`/`jwt_algorithm`, expire after `jwt_expire_minutes` (60 by default), carry `purpose="access"`, a unique `jti`, and an `sid` claim bound to `users.auth_session_id`; `get_current_user(...)` rejects tokens whose `sid` no longer matches the row in PostgreSQL (`backend/app/config.py`, `backend/app/services/auth.py`, `backend/app/core/dependencies.py`, `backend/app/models/user.py`). Every successful Google, GitHub, email-password, refresh, logout, and dev-token flow rotates `auth_session_id`, so the system effectively keeps one live bearer-token family per user and revokes older tokens by session mismatch rather than by maintaining a separate token blacklist (`backend/app/routes/auth.py`, `backend/app/services/auth.py`, `backend/tests/test_auth.py`).

Browser/CLI/mobile OAuth callbacks do not hand the long-lived app bearer token directly to the redirect target. After provider callback validation, the backend stores a random `pending_auth_code_id`, issues a signed auth code with `purpose="auth_exchange"`, and redirects with that short-lived code; `/api/auth/exchange` succeeds only when the embedded `code_id` still matches `users.pending_auth_code_id`, then rotates the auth session and clears the pending code. That makes the callback handoff single-use and time-bounded (300 seconds) rather than replayable across repeated exchanges (`backend/app/routes/auth.py`, `backend/app/services/auth.py`, `backend/app/models/user.py`, `backend/tests/test_auth.py`).

OAuth state validation is split by client type. Browser-initiated flows set an `oauth_state` cookie and require it to match the returned `state`; CLI and mobile encode the nonce into the `state` value itself, and mobile redirects are further constrained to `sacrifice://`, Expo schemes, or the configured frontend origin (`backend/app/routes/auth.py`). On web, the frontend keeps the resulting bearer token in `localStorage`; on native, it uses `expo-secure-store`; and the shared API wrapper attaches `Authorization: Bearer ...` to every request, clearing the token and dispatching a `sacrifice-session-expired` event after a 401 (`frontend/services/auth.ts`, `frontend/services/api.ts`, `frontend/__tests__/services/auth.test.ts`).

That bearer token gates financially meaningful user actions. The same `get_current_user(...)` dependency protects payment setup, payment-method listing and deletion, payment history, charity search, goal CRUD/proof submission, dashboard, notification, upload, and chat routes, so compromise of a still-valid token is equivalent to user impersonation until expiry, refresh rotation, or logout rotation invalidates it (`backend/app/core/dependencies.py`, `backend/app/routes/payment.py`, `backend/app/routes/goals.py`, `backend/app/routes/dashboard.py`, `backend/app/routes/notifications.py`, `backend/app/routes/uploads.py`, `backend/app/routes/chat.py`).

Goal-type extensibility currently starts at proof verification, not at full lifecycle creation. `backend/app/goal_types/registry.py` auto-discovers subpackages and `backend/app/routes/goals.py` resolves `goal.goal_type` through the registry for proof verification. The creation path still validates against a fixed allowlist in `backend/app/schemas/goal.py`, persists fixed PostgreSQL enums in `backend/app/models/goal.py`, and the frontend still hardcodes the same four-type union in `frontend/screens/GoalCreateScreen.tsx`.

The backend already publishes generator-friendly goal-type metadata. `GET /api/goal-types` iterates the registry and returns each type’s `name`, `description`, `sample_prompts`, and `criteria_schema`, but the current Expo goal-creation screen does not read that endpoint and instead renders its own fixed `GOAL_TYPES`/`GOAL_TYPE_LABEL` maps (`backend/app/routes/goals.py`, `frontend/screens/GoalCreateScreen.tsx`).

Proof submission is a JSON payload flow end to end. The frontend fetch wrapper always sends JSON bodies with `Content-Type: application/json`, and proof helpers in `frontend/services/api.ts` all post JSON objects. On the backend, proof data is flattened from the Pydantic model, stored in the `proof_submissions.proof_data` JSONB column, and returned with a separate verification-status shape (`frontend/services/api.ts`, `backend/app/routes/goals.py`, `backend/app/models/proof.py`).

Background work is configured but optional in day-to-day development. `backend/app/core/celery_app.py` builds a Redis-backed Celery app, includes per-goal worker modules via `get_celery_include_modules()`, and schedules deadline checks every 60 seconds. `PROMPT.md` explicitly says the orchestrator already runs backend and frontend, while Celery should only be started when a task genuinely needs it.

The mobile app is an Expo-managed single-app shell that uses local providers for auth and screen state. `frontend/App.tsx` loads fonts, holds splash-screen behavior, wraps `AuthProvider` and `NavigationProvider`, and switches among login, dashboard, goal creation/detail, proof submission, and notification screens by inspecting `currentScreen` instead of relying on a larger navigation framework.

Cross-machine migration is scripted rather than container-image-based. `scripts/migration/README.md` and `scripts/migration/bootstrap.sh` define a bundle/bootstrap flow that preserves `.env` files, `factory.db`, and the Sacrifice PostgreSQL dump, recreates Python and Node dependencies, starts Dockerized Postgres and Redis, runs Alembic, and smoke-tests the factory.

## Module map

| Module | Paths | Role | Current notes |
| --- | --- | --- | --- |
| backend | `backend/app/`, `backend/cli/` | FastAPI API, persistence, goal verification dispatch, optional workers, and CLI access to the same API | Registry-based proof verification exists, but goal creation and enums still hardcode four goal types. |
| frontend | `frontend/` | Expo mobile/web client for auth, goal creation, proof submission, dashboard, and notifications | The app sends JSON-only requests and the current plugin set does not expose camera or upload primitives. |
| migration | `scripts/migration/` | Bundle/bootstrap automation for moving factory and Sacrifice state between machines | The scripts preserve database and env state, but recreate Redis and dependency installs on the destination machine. |

## Current constraints
- Sacrifice does not use a separate refresh-token table or per-device session model. `/api/auth/refresh` accepts the current bearer token, rotates `users.auth_session_id`, and returns a new access token, so rotation revokes older tokens but also collapses each user onto one live bearer-token family at a time (`backend/app/routes/auth.py`, `backend/app/services/auth.py`, `backend/app/models/user.py`, `backend/tests/test_auth.py`).
- The web client stores the bearer token in `localStorage`, while native relies on `expo-secure-store`. That keeps browser refreshes simple, but any XSS-capable browser compromise can directly reuse the token against payment, goal, dashboard, notification, upload, and chat routes until expiry or server-side session rotation invalidates it (`frontend/services/auth.ts`, `frontend/services/api.ts`, `backend/app/core/dependencies.py`, `backend/app/routes/payment.py`).
- Email/password auth is still intentionally MVP-thin: the route comments call out missing email verification, missing password-reset/forgot-password flows, and no per-IP or per-email login/register rate limiting (`backend/app/routes/auth.py`).
- `GoalCreate` validation, `Goal`/`GoalCriteria` enums, and the goal-creation form still encode the built-in set `youtube_video`, `api_endpoint`, `dev_sandbox`, and `github_repo` (`backend/app/schemas/goal.py`, `backend/app/models/goal.py`, `frontend/screens/GoalCreateScreen.tsx`).
- Proof payloads are still JSON documents stored in JSONB, and the frontend API wrapper has no multipart or binary upload path (`frontend/services/api.ts`, `backend/app/routes/goals.py`, `backend/app/models/proof.py`).
- Expo configuration currently enables only `@react-native-community/datetimepicker`, `expo-secure-store`, and `expo-web-browser`, so camera/file capture is not wired into the mobile shell (`frontend/app.json`).
- Backend settings assume a local web frontend and a PostgreSQL/Redis dev stack, with OAuth, Stripe, YouTube, and Azure Foundry credentials provided through environment variables (`backend/app/config.py`).
- Backend CORS currently permits specific localhost web origins plus one ngrok hostname, and the app keeps a legacy `/auth/github/callback` redirect shim for GitHub OAuth (`backend/app/main.py`).
